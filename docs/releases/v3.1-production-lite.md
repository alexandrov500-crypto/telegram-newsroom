## Operational constraints

- Single-node T1 default; T2 requires Redis + `PUBLISH_LOCK_STRICT=1`
- ≤5 publishes/day initial cap (T1 week 1)
- Staging/test channel for validation — not production audience channels during sign-off
- `TELEGRAM_LIVE_VALIDATE=1` opt-in only
- Frozen `runtime/*.json` contracts unchanged

## Known limitations

- No distributed transaction between Telegram and SQLite (`FINALIZE_MISMATCH` possible)
- Partial multi-chunk publish may leave channel messages without DB finalize
- Telethon 2FA (`SessionPasswordNeededError`) not automated
- `publish_retries` counts publisher layer only
- 24h session longevity requires external supervisor (not CI)

## Rollback guidance

| Phase | Action |
|-------|--------|
| T0/T1 | `DRY_RUN=true`; stop scheduler/worker |
| Publish incident | Stop publish; inspect channel + DB |
| Lock/Redis | Single worker; fix Redis or disable multi-worker |
| Session | Re-auth per TELETHON_SESSION runbook |
